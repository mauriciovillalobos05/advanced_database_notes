# Session – 2026-03-10

### Topics covered
* **Cardinality:** The difference between High Cardinality (many unique values, e.g., emails) and Low Cardinality (few unique values, e.g., status flags or `site_id` 1–5).
* **Database Scan Types:** When the optimizer chooses a **Full Table Scan** versus an **Index Range Scan** or **Index Seek**.
* **Index Architecture:** How **B-Tree** indexes work (sorting, balancing, ranges) versus **Hash** indexes (exact matches only, no ranges).
* **Composite Indexes:** Multi-column indexes and the critical importance of the **Left-Prefix Rule** (Leading Column rule).
* **SARGability:** How wrapping columns in functions (like `TO_CHAR` or `TRUNC`) breaks the database's ability to use an index.
* **Performance Trade-offs:** The concept of **DML Overhead**—how indexes speed up reads (`SELECT`) but slow down writes (`INSERT`, `UPDATE`, `DELETE`).

## What I understood
* An index is not a magic wand; the database optimizer will ignore it if a query asks for a large percentage of the table (usually >5–10%) because a Full Table Scan is faster than bouncing between the index and the table.
* The order of columns in a composite index dictates its usefulness. If I have an index on `(patient_id, visit_date)`, a query filtering *only* by `visit_date` cannot efficiently use it.
* Columns must be left "naked" in the `WHERE` clause. It is always better to transform the input variable rather than the database column (e.g., `id = TO_NUMBER('123')` instead of `TO_CHAR(id) = '123'`).
* Designing database architecture requires balancing read speeds with write speeds depending on the system type (OLAP/Reporting vs. OLTP/Transactional).
